# 故事存档：从酒馆接着玩，也能把故事带走

首版围绕**一个单角色会话**：导入一段 SillyTavern 聊天，在原进度续写，再把 TipsyIsle 里新写的分支带到另一台设备。一个会话可以有多条路线；同一张卡的其他会话各自独立。

## 玩家怎么用

在「已保存会话」旁加「故事存档」，桌面用现有菜单和对话框，手机用底部菜单和系统文件选择器。馆藏的导入菜单也提供「导入故事存档」，让还没开卡的人找得到入口。

| 操作 | 玩家看到什么 | 确认后的结果 |
| --- | --- | --- |
| 导入酒馆聊天 | 选择 `.jsonl`，查看原角色名、消息数量、最后一条可见消息、可迁移的回复版本和变量。选择目标角色卡；缺卡时可先导入卡，再回来确认。 | 在目标角色下新建会话，旧会话不受影响。进入后停在上次聊到的地方，下一句由玩家自己发送。 |
| 导出 TipsyIsle 存档 | 选择当前会话或已保存的会话，查看路线数和随包带走的资源。 | 得到一个 `.tipsy-story` 文件，包含这个会话的全部路线和可恢复的剧情状态。 |
| 恢复 TipsyIsle 存档 | 查看存档来源、会话与路线数、随包资源、缺项和重名情况。 | 在空馆藏可以恢复出角色和会话；本机已有同一存档时，默认不重复导入，也可明确选择「另存为副本」。不会覆盖已有进度或同名资源。 |

例如，玩家从酒馆带来 328 条消息。预览可以显示「328 条消息 · 目标角色：圣樱学院」「正文和候选回复可恢复」「未找到可识别的世界书计时记录；计时会重新开始」。确认后直接打开第 328 条附近，保留导入时选中的回复版本。预览只显示纯文本，不运行角色脚本，也不发模型请求。

## 哪些数据能带走

| 内容 | SillyTavern `.jsonl` 导入 | TipsyIsle `.tipsy-story` 导出和恢复 |
| --- | --- | --- |
| 对话和进度 | 消息顺序、发言者、时间、隐藏状态、候选回复和选中的版本 | 完整消息树、候选回复、当前路线及对应版本 |
| 剧情状态 | 保留已识别的会话、消息和逐回复变量，例如能映射到当前运行环境的 MVU 数据。未知插件数据不当成已恢复的状态；缺少历史快照时不补造旧分支。 | 保留已保存的路线检查点、剧情变量、世界书计时和模板状态。切换路线时各自恢复；恢复操作不改写其他会话的资源。 |
| 角色和续写资源 | 聊天文件不一定包含卡、预设和世界书。绑定玩家选定的卡，沿用目标设备选定的预设，预览里列清需要补齐的资源。 | 随包带上这段会话关联的卡、可用的头像、预设、世界书及故事人设。按资源内容复用完全一致的本地副本；同名但不同内容时单独保存。 |
| 设备与扩展 | 不迁移酒馆设置目录、扩展安装和私有数据。首版不导入群聊，也不自动找回其他聊天文件里的书签或分支。 | 不打包 API 密钥、模型连接、局域网配对信息、插件程序与第三方插件私有数据。外置脚本、远程图片和独立图库不随包搬运；仍可保留原链接，预览明确标出依赖。 |

`.jsonl` 里某一楼的多个候选回复，不意味着文件里也有这些候选各自的后续剧情。比如最后实际沿着第 2 个回复写了十楼，导入后这十楼只接到第 2 个回复；第 1 个回复仍可选择，但不会凭空多出十楼。识别到依赖缺失时，可以查看已有正文，待补齐卡片依赖后再续写。

## 实现边界

1. **导入先预览，确认后一次保存。** 文件解析、消息清洗和资源匹配先在内存中完成。确认时若目标已删、切换中或正在生成，保留预览并提示何时能继续。会话、会话索引及新增资源通过现有存储事务一起落盘；写失败就不留下空会话或半份资源。保存成功后才切换会话并启动角色运行环境。失败行能定位到文件行号；首版不跳过损坏的正文行，以免导进一段缺楼的剧情。
2. **复用已有读写能力，别把兼容入口直接接到界面。** `importHelperChat` 目前依赖当前角色，会直接写档；`normalizeChatPayload` 可以作为起点。单独拆出不写存储的解析和预览，根据酒馆样本明确映射 `is_system` 隐藏语义、`swipe_info`、选中版本和变量。为每次导入分配新会话标识，按标识建立父楼和回复版本关联；保留明确支持的来源字段，未知字段不得改变应用设置。对完全一致的文件和目标角色提示已经导入，允许玩家显式另存副本。
3. **版本化、可独立恢复的存档包。** `.tipsy-story` 用 ZIP，内有 `manifest.json`、会话数据与资源。清单记录格式版本、消息和路线数量、资源清单及依赖。按明确字段清单构建导出数据，不直接打包应用数据库、全部全局变量或扩展设置。复用现有快照编解码思路来去重：同一份世界书或变量页在不同检查点中尽量只存一次，避免长篇档在手机上成倍膨胀。导出当前会话时先取最新已保存的状态，等待本轮结算完成。导入先校验格式版本、文件大小、资源引用、分支关系和选中路线；副本需一起重映射会话、消息、回复和资源引用。更高格式版本提示更新应用，不尝试降级恢复。
4. **三端使用相同格式。** 桌面和网页复用现有保存、下载入口；安卓用系统文件选择和保存流程，支持实际的文档 URI。解析和压缩在后台执行，预览可取消。验收时要确认安卓确实能把文件存到用户选定的位置，并从该位置重新选择导入。

## 开发顺序与验收

1. **先交付酒馆旧聊天导入。** 用真实导出的普通长篇、带重抽的聊天和一份 MVU 聊天验收。分别对照最后一条消息、选中回复、下一次生成时读到的变量。拿不支持的群聊和损坏文件验证错误提示及原存档不变。
2. **再接通 TipsyIsle 对外备份。** 用一个至少两条已续写路线的会话验证往返：两条路线里的物品归属、人物变量和世界书状态故意做成不同，在空馆藏的 Windows 或 Android 上恢复后切换验证。在有同名卡、同名世界书的设备上再次测试，确认旧资源和旧进度仍在。
3. **同一版把两段连起来测。** 从酒馆导出一个会话，导入 TipsyIsle，在第 328 条之后续写并开分支，再导出到另一台设备。恢复后打开的还是正确路线，不需要原设备在线。另测安卓取消、长篇文件、重复恢复和保存失败；完成后在存档预览和迁移指南同步列清首版的支持边界。

首版不要求整库搬迁、批量导入、聊天分享、云备份或所有酒馆插件状态。先完成「一份旧故事带进来，一份新故事完整带走」的往返。
